## 決めた仕様と理由

| 項目 | v0.1 の選択 | 理由 |
| --- | --- | --- |
| 対象 | 会話の保存フィルターのみ | 既存の連絡先・レポート機能へ広げない |
| 共有範囲 | 同一アカウント内の1チーム | 複数チームや公開リンクの仕様を持ち込まない |
| 作成 | 所属メンバー、または同一アカウント管理者 | 普通の担当者が自分のチームのために作れる |
| 閲覧・利用 | 現メンバーと同一アカウント管理者 | チームの業務資産として扱う |
| 編集・削除 | 所属中の作成者と同一アカウント管理者 | 他メンバーが意図せず業務条件を変更しない |
| 作成者脱退・削除 | ビューは残る。管理者が保守可能 | 個人の退職によってチームの業務条件が消えない |
| チーム削除 | 共有ビューは利用不可 | 自動的に公開・個人化しない |
| 会話閲覧 | 利用者自身の既存権限の範囲内 | フィルターの共有をデータの共有権限と混同しない |
| 共有先変更 | v0では作成後の変更なし | 共有解除・所有権移転を含む別の設計問題を避ける |
| 個人ビュー | そのまま残す | 実在する機能を人工的に削除して難しくしない |

管理者は所属チーム外の共有ビューを管理できるが、他人の個人ビューを読める
ようにはしない。作成者の脱退後もビューを残す要件は、既存の User →
custom_filters の非同期削除と整合させる必要がある。これは隠れた採点条件に
せず、課題文 R5 に明記した。

共有先は閲覧者の集合であり、会話の担当チーム条件ではない。例えばSupport
チームの共有ビューでも、クエリが `status=open` なら、各利用者が閲覧できる
全Open会話が対象となる。

APIの `team_id` は外部仕様として固定する。一方、テーブル分割、関連付け、
サービス層、キャッシュ実装、UI配置、作業分担は指定しない。実装ごとに評価器の
期待するAPIを推測させることを避けつつ、実装の自由を保つ。

## 固定する土台

- Upstream: `https://github.com/chatwoot/chatwoot`
- Commit: `5b7038b950b763e230df2d544df9b87b8752fef3`
- Edition: Community (`DISABLE_ENTERPRISE=true`)
- 既存個人フィルター、チーム、会話、権限チェック、既存テストを保持する。
- 完全なソースと既存のライセンス表示を保持し、enterprise機能を課題に使わない。
  再配布用パッケージのライセンス・依存物表示確認はパッケージ作成時に行う。
- 配布イメージは取得済み依存関係とブラウザを含め、試行前に起動確認する。
  upstream commitとlockfileに加え、実行イメージdigest、CPU/メモリ上限、
  ブラウザ版、fixture版、課題版、評価器版をrun manifestへ記録する。
- 試行ごとにソースとDBを初期化する。別試行の編集・DB・Redis状態を引き継がない。

2026-09-17のローカル実験では、関連する既存RSpec 56件、Vitest 120件が合格。
個人ビューのAPI操作、UIから保存・再読み込み、他ユーザーの非表示も確認した。
初回の並列ビルドは強制終了し、Docker再起動後にgRPC等の並列数を2に抑えると
成功した。Ruby依存構築は約9分46秒、frontend依存は約13秒。
画面確認時のサービス合計メモリは約1.7〜2.2GiBだった。
これは本番タスクの必要メモリ上限、全テスト成功、共有機能の品質の証拠ではない。
詳細ログとローカル起動構成は `local/chatwoot-feasibility-20260917/` にあり、
Git管理外の実験資料である。この案の動作保証に必要な資材は今後正式にパッケージ化する。

## 公開fixture案

全員が架空のユーザー。パスワードや外部APIキーを必要とする本物の業務データを使わない。
表中の名前はラベルであり、非公開テストは数値ID・名前・件数を変えてよい。
非公開にしてよいのは具体値だけで、以下の権限や必須挙動は隠さない。

| アカウント | ユーザー | ロール | 初期所属チーム | 閲覧可能なinbox |
| --- | --- | --- | --- | --- |
| A | Admin | 管理者 | なし | Aの全inbox（既存管理者権限） |
| A | Alice | 一般担当者 | Support | General, Restricted |
| A | Bob | 一般担当者 | Support | General |
| A | Carol | 一般担当者 | Billing | General |
| A | Dana | 一般担当者 | Support | なし |
| A | Erin | 一般担当者 | なし | General |
| B | ForeignAdmin | 管理者 | Support-B | Bの全inbox |

アカウントA: GeneralにOpen 3件、Resolved 1件、RestrictedにOpen 2件、Resolved
1件。アカウントB: Open 2件。会話は未担当・別チーム担当を混ぜ、Support担当だけに
誤って絞る実装を検出する。固定時刻・既知の既読状態とメッセージを用意する。
クエリ `status=open` のSupport共有ビューは Alice/Adminに5件、Bobに3件、Danaに
0件を返す。Carol/Erin/ForeignAdminは共有ビュー自体を利用できない。

移行前DBにはAlice/Bobの個人会話ビュー、連絡先・レポートフィルターを保存する。
既存で有効な単一条件・AND/OR複合条件・current-user条件を含める。これらの具体的な
クエリは固定コミットの公開APIで有効性を確かめてからfixtureを確定する。
同名の個人ビューを異なる所有者へ、同名の共有ビューを異なるチームへ用意し、
名前による照合や権限判定を検出する。

状態変化は独立fixtureで順に検証する:

1. ErinをSupportに追加 → 同じセッションの次のリクエストから利用可。
2. キャッシュを温めてBobをSupportから削除 → 次のリクエストからビュー利用不可。
3. BobのGeneral閲覧権限だけを削除 → ビューは利用可、会話・件数は0。
4. Aliceのチーム脱退、アカウント脱退、ユーザー削除を別々に実行 → ビューは残り、Adminが編集可能。
5. 生存するAliceをSupportに再追加 → 作成者として編集可能。
6. Supportを削除 → その共有ビューだけ利用不可。Billingのビューと存続ユーザーの個人ビューは保持。

初回の起動検証用seedは全ユーザーが同じinboxを見られるため、このfixtureの代わり
にはならない。fixtureは本番タスク用の新規DBで実装し、現在のプレビューは保持する。

## 受け入れ条件との対応

「合格」には全必須グループを満たす必要がある。グループ別結果は失敗箇所の説明用で、
制限時間内の達成点数を競う方式にはしない。

| 公開要件 | 自動確認する結果 | 主な誤実装 |
| --- | --- | --- |
| R1 | 既存DBからmigrate、既存行のID/所有者/クエリ等を比較、個人CRUD、再起動後の永続化、新規DB起動 | DBを作り直す、全既存ビューを共有化する |
| R2 | 有効な共有作成、複合クエリ、current-user、同名、無効/別account team、空名、対象filter_type | 名前固定、他accountチーム、Support担当に暗黙限定 |
| R3 | 権限表の各actorでcollection/read/create/update/delete。拒否前後で状態比較 | UIだけの制限、他メンバーの編集、管理者の個人ビュー漏洩 |
| R4 | 制限inbox、ゼロ件、pagination/count/unread、直接の会話アクセス、キャッシュ済みの別ユーザー | 作者の権限で会話表示、共通キャッシュ経由の漏洩 |
| R5 | 同一セッションで所属/inbox変更、作者/チーム削除、非同期ジョブ処理前後、影響外データ比較 | 古い権限キャッシュ、作者削除で共有ビュー消失、team削除で個人化 |
| R6 | 公開API契約、旧payload、型別一覧、重複なし、audience不変、偽造owner/account、エラー分類 | 旧client破壊、PATCHで共有解除、mass assignment |
| R7 | UI作成・閲覧・更新・削除・再訪、非編集メンバー、422/通信失敗の表示と入力保持、キーボード操作 | APIだけ実装、保存失敗を成功表示、UI管理権限不整合 |
| R8 | 起動/build、固定した既存回帰テスト、追加テスト、変更ソースのlint、検証メモ | テスト削除で見かけの合格、起動不能、不要な全面変更 |

未実装の基準版はR2/R3/R6/R7を失敗する必要がある。既存個人ビューの成功だけで
課題を合格にしてはいけない。

## 評価器の設計

- agentのコンテナを停止して成果物を取得し、認証情報のない新しい検証環境へ適用する。
  元DBを持ち込まず、公開fixtureの基準DBからmigrationする。候補コードをホストで実行しない。
- Rails/DB/Redis/browserを含む検証側のサービス構成と起動順は新規実装が必要。
  現行の単一コンテナ評価がそのまま使えるとは扱わない。
- 既存回帰テストは信頼できる固定コミットのものを使用する。候補がテストや評価出力を
  書き換えても合格の根拠にしない。private testはagent環境へ配置しない。
- 新APIはHTTPで評価し、UIはPlaywrightで実際に操作する。新しいschemaの列名や
  コントローラー構成は検査しない。必要なexpected値は評価側のfixtureから独立に求める。
- UIの文言・CSS selectorを非公開の正解にしない。表示ラベル/roleを基準にする。
  自動化に厳密なUI契約が必要になった場合は、全候補共通の最小操作契約を課題文へ
  公開してから試行する。事後的に候補ごとの特例や採点変更を加えない。
- 会話の正解集合は既知のaccount/inbox権限とqueryから求める。
  同じ候補の別APIの値と一致したことだけを正解の根拠にしない。
- 非同期削除は「直後に権限が消える」と「ジョブ完了後にも正しい」の両方を確認。
  時間経過のsleepだけに頼らず、コミット/ジョブ完了を明示的に待つ。
- 画面の操作ログ、API status、失敗条件、DB移行結果、build/test結果を保存する。
  合否に必要な事実と環境エラーを区別し、候補自身の「成功した」という記述は採点に使わない。

評価器の自己検証では、少なくとも「基準版」「正しい参照実装」「UIのみ共有」「account隔離なし」
「会話のinbox制限なし」「作者削除で共有ビュー消失」「キャッシュ失効なし」の候補を使い、
それぞれ想定した理由で成功/失敗するか確認する。正しい別実装を少なくとも1つ受け入れ、
内部設計に依存した誤判定がないかも確認する。

## 時間切れと人によるレビュー

- 初回イメージbuild・起動確認・fixture投入を課題実行前に完了する。
- 作業開始から終了までのwall time、取得可能なtokens/cost、呼び出し数を別途記録する。
  計測不能値は不明とし、0としない。モデル・effort・ツール・資源を揃えて比較する。
- 異常な長時間処理を止めるwall-clockの安全上限は残す。最初の試行では4時間を暫定案とし、
  参照実装/試走で妥当性を確認して全候補に事前公開する。現在のsuiteの時間設定は変更しない。
- `execution_status`（完了/安全上限停止/基盤障害/利用上限）と
  `correctness`（pass/fail/unscored）を分ける。停止だけを理由に自動的に不正解にしない。
  回収可能な成果物を通常の検証器に通し、全要件を満たせばpass、確認できた違反はfail、
  環境不備などで判定できなければunscoredとする。実行が完了したかどうかも併記する。
- 利用上限では自動再試行・チケット使用・追加購入・別モデルへの切り替えを行わない。
- 人はスクリーンショットと同じ操作シナリオで、共有先の分かりやすさ、個人/共有の区別、
  権限の伝わりやすさ、既存UIとの整合性をレビューする。
  良い/要改善/問題ありと具体的根拠を記録し、自動合否へ混ぜない。LLM judgeは必須にしない。

## Issue14への適合レビュー

| Issue14の方針 | この案での対応 |
| --- | --- |
| 実在する大きめの既存アプリでの開発 | Chatwoot固定コミットの保存機能を拡張 |
| 高水準でも曖昧な課題にしない | 権限表・API外部仕様・ライフサイクルを公開 |
| 分解・設計判断をagentへ残す | schema/内部構造/UI配置/担当分割は自由 |
| 個人で動かせる規模 | 起動検証済み構成を再利用。長いbuildは事前準備 |
| 自動判定と人の判断を分ける | 要件R1〜R8の検証と別枠UXレビュー |
| 固定予算内の進捗点数にしない | 最終成果物の正しさと時間/費用を別記録 |
| 一つずつ作り、実測して改良 | この1課題だけ仕様化。別カテゴリの課題は追加しない |

この課題が単一エージェントに不可能、または複数エージェントが優位とは主張しない。
複数層にまたがる要件はあるが、難易度と比較の有用性は実測で判断する。

   課題・評価器を変更した場合は版を上げ、旧結果を保持し、比較する全候補を同じ版で再実行する。

## 実装の進捗（2026-09-17）

[初期ハーネス](../../../experiments/chatwoot-team-views/README.md)を実装した。
固定コミットの独立checkout、初回のみのDB初期化、制限inboxを含むfixture、HTTP probe、
既存フォルダーのブラウザsmoke、評価器/初期化保護のunit testを含む。

新規DBで既存機能11件が全て成功し、共有機能は13件成功・20件が想定した未実装理由で失敗した。
後片付け7件は成功したが機能スコアには含めない。ブラウザではAliceに5件、Bobに3件を表示。

この結果は「土台と初期probeが動く」証拠であり、全要件の評価器完成ではない。
正しい参照実装との照合や、上記R1/R5/R7等の未完了範囲が残っているため、
出力は意図的に `correctness: unscored`、`qualified_for_agent_comparison: false` とする。

## 成果物転送と隔離検証の追加（2026-09-17）

[隔離ランナー](../../../experiments/chatwoot-team-views/ISOLATED.md)を追加した。
追跡済みソースをハッシュ付きZIPに固定し、Git情報・ホストマウント・agent認証情報を
渡さず、専用Dockerボリュームで実行する。初期データは固定した上流版で作成し、
候補コードの通常マイグレーションで更新する。候補アプリは非root・権限削減状態で動かし、
実際のマウントとネットワーク設定も検査する。

参照成果物では個人用4件の保持、HTTP45件、再起動、UI5フローが成功した。
同じ経路に未実装の上流成果物を渡すと、既存機能は通り共有要件20件で失敗した。
公開JSON操作マップにより、UIのボタン文言や配置を採点ロジックから分離した。
マップは操作対象の指定のみで、候補側のJavaScriptや合格条件を実行しない。

これは採点器の部分的な対照検証であり、まだ全要件の採点完了ではない。
残作業は残りのUI操作・ライフサイクルの外部検証、回帰/build/lintの統合、
ブラウザの固定・配布環境、完全な経路での誤実装/正常変種の検証。
詳細な結果は `experiments/chatwoot-team-views/isolated-evidence.json` に記録する。
